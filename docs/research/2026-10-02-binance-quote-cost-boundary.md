# Binance Web3 quote cost boundary

**Checked:** 2026-10-02. **Method:** official documentation review against the [sanitized live quote](2026-10-02-first-live-binance-quote.md). A later [signed `/swap` build](2026-10-02-first-live-swap-build.md) supplied a direct comparison with the quote gas fields; it did not sign or broadcast a wallet transaction.

| Field or step | Official description | What the live NVDAB read establishes |
|---|---|---|
| `toTokenAmount` | [Trading API reference](https://web3.binance.com/en/dev-docs/catalog/web3-wallet/api/rest-api/trading-api): estimated buy-token amount in smallest units, returned by the vendor | The observed 18-decimal raw output is an estimated USDT amount, not settled proceeds. |
| `tradeFee` | Same reference: estimated network fee in USD, nullable | The observed `0.01800319` is labelled a network-fee estimate. The docs don't establish that subtracting it from `toTokenAmount` gives net USDT, or whether it includes approval. |
| `estimateGasFee` | Same reference: estimated gas in the chain's smallest unit, with example `150000` | A later same-quote `/swap` build returned `tx.gas=450000` and a separate `tx.gasPrice=107761879` wei. For this route, the field behaved as estimated gas units, not paid wei. No gas was paid. |
| `feeAmount` and `feeToken` | Same reference: populated for an enabled custom referral fee | Both were null in the observed request, which supplied no custom referral fee. This doesn't establish zero venue, gas or execution costs. |
| `executionMode` | [Trading API introduction](https://web3.binance.com/en/dev-docs/products/trading-api/introduction): bStocks may return LiquidMesh `SWAP` or PcsXRfq `RFQ`; SWAP follows quote, build swap, sign, broadcast | The NVDAB quote returned LiquidMesh `SWAP`. The [endpoint reference](https://web3.binance.com/en/dev-docs/catalog/web3-wallet/api/rest-api/trading-api) still says RWA always RFQ. The route mode is observed; its actual transaction path wasn't run. |

**Decision:** keep the main sale card Unquoted and the separate Sale check as a short-lived *estimated output* with review-required mode. The unsigned SWAP transaction build now works for one temporary address, and the gas-unit interpretation is supported for that route. No net-proceeds number or sell-versus-borrow recommendation can be calculated from these fields alone. A same-wallet, same-amount holder task, allowance and gas checks, execution-path validation and observed costs are needed before changing that claim. The [mentor question](mentor-questions.md) still needs confirmation of included vendor fees and approval gas; it hasn't been sent.

## 3 October documentation and arithmetic update

The [current Binance Trading API reference](https://web3.binance.com/en/dev-docs/catalog/web3-wallet/api/rest-api/trading-api), checked on 2026-10-03, defines `tx.minReceiveAmount` as the smallest-unit buy-token minimum at the chosen slippage and `tradeFee` as an estimated network fee in USD. For the single [1 NVDAB unsigned build](2026-10-02-first-live-swap-build.md), the observed `tx.gas=450000` and `tx.gasPrice=107761879` wei imply a multiplication of **48,492,845,550,000 wei**, or **0.00004849284555 BNB**, if the transaction consumed its full gas limit at that gas price. The same build reported `tradeFee=0.03371889` USD and `minReceiveAmount=232977404098026021909` raw USDT units, or 232.977404098026021909 USDT, at a requested 0.5% slippage. These are pre-sign fields for one nonholder request. The minimum isn't a fill, and the BNB gas budget isn't a paid fee. The amount and method of an approval transaction remain unknown.

The main Sell card now displays a fresh, input-matched **estimated output before costs** beside the Venus illustration under [D-029](../decisions/decision-log.md); the older Unquoted display decision above describes the 2 October screen. It still doesn't display net proceeds or recommend sale over borrowing. A holder-sized build, allowance check and observed execution-cost semantics remain required for a personal cash decision.
