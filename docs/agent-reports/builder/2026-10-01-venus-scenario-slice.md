# Venus scenario slice builder report

**Date:** 2026-10-01

Implemented `app/server.py`, `app/index.html` and updated `README.md` for a local, read-only NVDAB versus USDT scenario. The server binds to `127.0.0.1`, fetches the public Venus market API once per calculation, selects NVDAB and USDT by verified underlying contract on chain 56, requires a unique USDT market in the NVDAB market's pool, and validates listing, collateral, prices and USDT borrowability. Collateral capacity, health factor and liquidation stress convert USD oracle values to USDT units using the USDT oracle price. Inputs are bounded to avoid extreme Decimal magnitudes. The UI says Venus API values are indexed, can lag the chain and are not transaction-safety data; pool cash does not guarantee a borrow. The sale remains explicitly unquoted.

**Limits and risks:** the [Venus API documentation](https://github.com/VenusProtocol/venus-protocol-documentation/blob/main/services/api.md) warns indexed data can lag and is not authoritative for live prices, market pause state or liquidation safety. The app has a narrow Core membership and pool-selection notice, but no account balances, debt state, personal borrow or liquidation calculation, verified proceeds or execution. The simplified health factor excludes other positions and protocol protections. No tests or build commands were run, as requested.

## Optional wallet balance read

Added a separate `POST /api/balance` flow. It accepts the public address and entered NVDAB units in the request body, verifies `eth_chainId` is 56, chooses one block number, reads NVDAB contract code and `decimals()` at that block, requires 18 decimals, and calls `balanceOf` at that same block. The UI shows exact token units, block number/tag and block time, plus whether the entered units are covered. Failed RPC or metadata validation leaves the balance explicitly unknown. App access logs do not include POST bodies, response data omits the address, and the browser does not persist it. The public RPC receives the address in `balanceOf` calldata.

The public address is not proof of address control, product eligibility or jurisdiction. The Venus scenario remains isolated and has no wallet debt/collateral or personal liquidation calculation. The [official BNB Chain endpoint documentation](https://docs.bnbchain.org/bnb-smart-chain/developers/json_rpc/json-rpc-endpoint/) lists the configured mainnet RPC and chain ID 56. No tests or build commands were run.

## Optional Venus Core account-state notice

Added an independent local `POST /api/venus-account` read for the public wallet already entered on the page. It checks chain ID 56 and Core Unitroller code at one BNB block, then calls `getAssetsIn(address)` and the direct `userPoolId(address)` getter at that same block. It validates the dynamic address-array ABI and limits it to 64 entries, validates returned addresses and uniqueness, and bounds the selected pool value to `uint96`. The display reports entered Core market count, selected pool ID, block and timestamps. Nonempty membership or nonzero pool selection is labelled as existing Core configuration. Empty membership and pool 0 are only observations, not proof of no debt elsewhere or safe borrowing. Any RPC or ABI failure leaves account state unknown. The route is independent of the Venus market API and Binance quote flow; the wallet is sent only in a local POST body and isn't returned, logged or stored.

The selector gate was verified against official Venus source and a fixed-block RPC read documented in [the account-state boundary note](../research/2026-10-01-venus-account-state-boundary.md). `getAssetsIn(address)` resolved through the Diamond selector map, while `userPoolId(address)` succeeded as a direct inherited public getter at block 125170964 despite having no mapped facet. This is a membership/pool notice only. No holder account was queried for this implementation report; no account debt, collateral balance, borrow feasibility or personal liquidation outcome is shown.

## Optional Binance quote observation

Added a separate local `POST /api/quote` path, independent of Venus scenario fetches and the wallet balance read. It requires both Binance Web3 credentials from the process environment or an ignored root `.env`; missing credentials produce a local status without an upstream call. Each explicit UI click validates the public address and amount, makes one signed `GET /build/api/v1/dex/market/rwa/search?keyword=NVDA&platformId=bstock`, and requires exactly one well-formed identity matching ticker NVDA, platform `bstock`, chain 56, the pinned NVDAB contract, symbol NVDAB and `assetType=1` (Stock). Missing, ambiguous or malformed identity data blocks the quote call. Only after identity passes, the server verifies NVDAB code and `decimals()` at one BNB block, converts NVDAB units to a raw integer amount, then makes at most one signed `GET /api/v1/dex/aggregator/quote`. The local POST requires JSON, rejects foreign origins and unexpected Host values, and does not follow redirects or call swap, approval, order or broadcast endpoints. Local request logging omits paths and bodies; output excludes wallet, signed URL, headers, quote IDs, raw messages and payload.

The route parser now requires chain 56; exact NVDAB/USDT contract and symbol metadata; documented `decimal="18"` fields matching both tokens' on-chain code and `decimals()` reads at one BNB block; an integer-string `fromTokenAmount` equal to the request; and a positive integer-string `toTokenAmount`. It returns only sanitized route count, vendor, mode, validated amount strings, capture time, latency, metadata block and fixed error labels. The official [Trading API reference](https://web3.binance.com/en/dev-docs/catalog/web3-wallet/api/rest-api/trading-api) defines amount fields as token smallest-unit integers. Its statement that equity/RWA routes always use `RFQ` conflicts with the [Trading API introduction](https://web3.binance.com/en/dev-docs/products/trading-api/introduction), which describes mixed bStock `SWAP` and `RFQ` routes. No live NVDAB quote response or cost review has been made, so the UI does not calculate USDT proceeds and the sale stays **Unquoted**; any `SWAP` mode for NVDAB is flagged for review. HTTP success is accepted only alongside business `code=0` and a list-shaped route payload. [Binance documents HMAC-SHA256 over timestamp, method and the encoded `/build` path plus query](https://web3.binance.com/en/dev-docs/authentication). BNB codes 40421 and 40441 map to no route; BStock 40369/40370 distinguish market closure and unsupported pair.

This is a partial read-only slice against the one-page spec. It implements the signed RWA identity search gate but does not implement account-wide Venus state, wallet-specific risk or any sale execution. The official RWA reference defines `assetType=1` as Stock, which is required for this NVDA stock identity. No live signed search or quote was made. A returned route's amount units, fee scope, net proceeds and final execution are unverified. The sale card remains **Unquoted**. The wallet is sent in Binance's request query as required for potential RFQ routing; the page explains this and does not put the wallet in the local app URL, response, logs or storage. No tests or build commands were run.

## Input consistency review

Static review found that changing NVDAB units or the USDT target could leave a scenario calculated for the previous inputs on screen while the other actions used the new values. `app/index.html` now clears the affected scenario, balance and quote displays when their inputs change. Independent request generations also discard late responses after an input edit. This avoids presenting two different input states as one decision. The change was reviewed as a diff; no browser session, test or build was run.
