# BNB tokenized stocks project

Working repository for a new Dyplux entry to [BNB Hack: Tokenized Stocks Edition](https://www.bnbchain.org/en/hackathons/tokenized-stocks). The provisional product test compares an NVDAB sale with a Venus USDT borrowing scenario for the same cash target.

## Run the read-only Venus scenario

Requires Python 3.9 or newer and no installed packages. From the repository root, run:

```sh
python3 app/server.py
```

Open `http://127.0.0.1:8000`. Enter NVDAB units and a USDT target, then select **Fetch scenario**. Each request retrieves an indexed snapshot from the public Venus API. The JSON endpoint is `GET /api/scenario?units=1&cash=100`. The request uses `accept-version: next` because the current `stable` response carries a migration warning; the [dated version check](docs/research/2026-10-02-venus-api-version-check.md) records the observed response shapes.

The result appears directly below the amounts. The sell path stays **Unquoted**; the borrow path is a hypothetical market illustration. The sale card links to a separate **Sale check**: enter a public address there and select **Estimate partial sale**. The check sizes a candidate NVDAB sale against the same USDT cash target, using one probe quote and at most one candidate quote. It shows the candidate amount, an approximate output and whether the exact raw output reaches the target before costs. The evidence and limits are expandable. Editing the target or units clears the estimate, which expires after 20 seconds. An invalid target blocks the request. None of this establishes net proceeds or gives a sale instruction. The borrow card keeps the principal checks visible and puts exact values, oracle inputs and isolated risk illustrations under **Exact values, oracle inputs and borrow assumptions**. Balance and Venus Core reads are under **Optional balance and Venus Core reads**.

An optional public wallet address reads the NVDAB ERC-20 balance through the [official BNB Chain mainnet RPC](https://docs.bnbchain.org/bnb-smart-chain/developers/json_rpc/json-rpc-endpoint/). The server checks chain ID 56, reads contract code and `decimals()` metadata, then calls `balanceOf` at one recorded block. It reports that balance and whether it covers the entered sale units. RPC failure leaves the balance unknown. The address is sent in a POST body, not a URL. The public RPC receives the address in the balance request; this app does not write it to application logs or storage. A public address does not prove ownership or jurisdiction eligibility. This read does not inspect Venus positions.

The separate **Read Venus Core account state** action sends the same optional public wallet in a local JSON POST body to `POST /api/venus-account`. It verifies chain ID 56 and Core Unitroller code, then reads `getAssetsIn(address)`, the direct `userPoolId(address)` getter, `getBorrowingPower(address)` and `getAccountLiquidity(address)` at one recorded block through Core Unitroller `0xfD36E2c2a6789Db23113685031d7F16329158384`. The entered-market array is strictly bounded, the pool ID is validated as `uint96`, and both three-word risk results fail closed on ABI or contract errors. The display shows current net borrowing-power and liquidation-threshold states as **cushion**, **shortfall** or **zero**, plus Core market count, pool ID, block and timestamp. It does not return raw risk values or read gross supply/debt balances. These current net states are not a health factor, a USD amount, a post-deposit forecast or proof that a new borrow is available. A nonempty market list or nonzero pool ID flags existing Core configuration. An empty list and pool 0 do not establish no debt elsewhere or safe borrowing. RPC or ABI failures leave the account state unknown. The address is not returned, logged or stored. A live read of two documented empty/default addresses checked response shape only; no consenting holder or populated risk position has been observed.

The optional **Estimate partial sale** action requires `BINANCE_WEB3_API_KEY` and `BINANCE_WEB3_SECRET_KEY` in the process environment or in the ignored repository-root `.env`. Each explicit click first makes one signed, read-only RWA search for `NVDA` on `bstock`. The server requires exactly one result with ticker NVDA, platform BStock, chain 56, the pinned NVDAB contract, symbol NVDAB and stock `assetType=1`; missing, ambiguous or malformed identity data blocks the quote call. Only after that check, it verifies NVDAB's decimals at a recorded BNB block and makes one signed `GET /api/v1/dex/aggregator/quote` for a probe of at most 1 NVDAB. It calculates a candidate sale in integer raw units, caps it at the typed holding and requests at most one more signed quote if the candidate differs. It doesn't keep increasing the amount until a target is reached. The wallet is sent to Binance in quote queries, but isn't put in this app's URL, response or logs. Missing credentials, identity failures, RPC errors, no route and documented API errors are shown as distinct states. A route observation isn't verified USDT proceeds: fee scope and execution remain unestablished. No quote is stored, and the app never requests approval, swap construction, order submission or transaction broadcast. Signing follows the [official authentication guide](https://web3.binance.com/en/dev-docs/authentication), [RWA search reference](https://web3.binance.com/en/dev-docs/llms-full.txt) and [Trading API guide](https://web3.binance.com/en/dev-docs/llms-full.txt). A [dated fractional technical read](docs/research/2026-10-02-fractional-target-quote.md) returned a 0.43 NVDAB SWAP quote near a 100 USDT target; it didn't use a holder or execute a sale.

Run `python3 -m unittest discover -s tests -v` for local checks. The Binance quote-flow tests use synthetic responses and an in-memory RPC substitute. They exercise identity rejection, route amount matching and removal of quote IDs from the app response. The separate dated live request established authentication and one technical route, not holder execution or a safe cash decision.

The Venus panel remains a market-level illustration only, with no wallet debt or collateral, verified net sale proceeds, order, transaction, or execution. The sale card stays **Unquoted** and reports no proceeds, even if a quote route is observed. The separate Sale check can show the route's approximate estimated USDT output; it expires quickly and isn't a final received amount. Borrow capacity, hypothetical health factor, liquidation-price stress, pool cash and flat-rate interest figures use isolated assumptions and do not establish personal safety or guarantee borrowing. The panel checks the typed NVDAB units against indexed Venus supply-cap headroom and separately reads the Core cap, vNVDAB supply and stored exchange rate at one recorded BNB Chain block. It verifies chain 56, deployed code and the vNVDAB underlying before displaying contract headroom. If any contract read fails, the contract check says **Unknown**; an indexed estimate never substitutes for a passing contract check. The panel also calculates the exact collateral-only minimum for the cash target from indexed oracle prices and the base collateral factor, rounded up to one NVDAB base unit, and compares it with the recorded cap. The minimum has no safety buffer, fees or account-wide risk check, and isn't a recommended deposit. Neither a passed cap check nor an indexed minimum establishes that a supply or borrow transaction can execute. [Venus says its indexed API can lag chain state](https://github.com/VenusProtocol/venus-protocol-documentation/blob/main/services/api.md); inspect both displayed source times.

On 2026-10-02, a [read-only technical quote](docs/research/2026-10-02-first-live-binance-quote.md) authenticated with Binance Web3 and returned one LiquidMesh `SWAP` route for 1 NVDAB to USDT. It used a temporary nonholder address and wasn't an executable user sale. The app marks this mode for review because the [endpoint reference](https://web3.binance.com/en/dev-docs/catalog/web3-wallet/api/rest-api/trading-api) says RWA routes always use `RFQ`; it still withholds net proceeds and any sell-versus-borrow recommendation.

A later [read-only `/swap` build](docs/research/2026-10-02-first-live-swap-build.md) returned an unsigned LiquidMesh transaction payload for a fresh technical quote. In that one response, quote `estimateGasFee=450000` matched `tx.gas=450000`, while `tx.gasPrice` was separate. The request did not sign, simulate or broadcast a trade, and the temporary address had no verified holdings or allowance. The app still treats the sale as an estimate with unverified proceeds.

## Prepare Binance Web3 credentials

On the SSD, store a full key pair only in the ignored repository file `/Volumes/SSD500/Dyplux/bnb-tokenized-stocks-2026/.env`, setting `BINANCE_WEB3_API_KEY` and `BINANCE_WEB3_SECRET_KEY`. An unquoted value is accepted by the local loader. Do not put either secret in chat, commits, logs or demos. Start the server from the repository root with `python3 app/server.py`, then open `http://127.0.0.1:8000`. The **Estimate partial sale** action performs one signed, read-only RWA identity search and, only when that identity is unambiguous, one or two signed quote requests for the entered cash goal and public wallet. It doesn't submit, approve or broadcast a transaction. Keep the pair in `.env` only; use `.env.example` as the empty-field template.
