# BNB tokenized stocks project

Working repository for a new Dyplux entry to [BNB Hack: Tokenized Stocks Edition](https://www.bnbchain.org/en/hackathons/tokenized-stocks). The active product hypothesis is a **pre-entry exit check** for a small NVDAB purchase on BNB Chain. The earlier NVDAB sale versus Venus borrowing comparison is preserved as research, with its original claim retired in [D-045](docs/decisions/decision-log.md).

## Run the pre-entry exit check

Requires Python 3.9 or newer, no installed packages, and Binance Web3 API credentials for live quotes. From the repository root:

```sh
python3 app/server.py
```

Open `http://127.0.0.1:8000`. Enter a positive USDC amount up to 100 and a **public** BNB Chain address, then select **Check both routes**. The server verifies the pinned NVDAB bStock identity with Binance Web3 RWA search and token metadata at a recorded BNB Chain block. It requests a USDC-to-NVDAB quote, then an immediate NVDAB-to-USDC quote for the first quote's estimated output. The page distinguishes both routes quoted, no entry route, no inverse route and an incomplete check. It shows each estimate, provider route, fee estimate when provided and receipt time. The visible result expires 20 seconds after the local request begins.

Set `BINANCE_WEB3_API_KEY` and `BINANCE_WEB3_SECRET_KEY` in the process environment or the Git-ignored repository `.env`. The [empty template](.env.example) shows the names. Requests are signed on the local server. The page never asks for a private key, connects a wallet, signs, builds or broadcasts a transaction. A public address is sent to the provider for address-specific quotes; it isn't returned or stored by this app. No Binance exchange account is needed for this read-only check.

**What the result means:** an immediate inverse route is a quote observation, not proof of issuer eligibility, actual fill, recoverable proceeds, a later exit or profit. Approval cost, gas payment, slippage minimum and execution stay unknown. The code currently binds to localhost and has no public deployment. See the [one-page spec](docs/product/pre-entry-exit-spec.md), [current status](docs/status.md), [research receipt](docs/research/2026-10-03-usdc-nvdab-roundtrip-quote.md) and [DX log](docs/dx/field-log.md).

## Archived research: read-only Venus scenario

Requires Python 3.9 or newer and no installed packages. From the repository root, run:

```sh
python3 app/server.py
```

Open `http://127.0.0.1:8000/venus-scenario`. Enter NVDAB units and a USDT target, then select **Fetch scenario**. Each request retrieves an indexed snapshot from the public Venus API. The JSON endpoint is `GET /api/scenario?units=1&cash=100`. The request uses `accept-version: next` because the current `stable` response carries a migration warning; the [dated version check](docs/research/2026-10-02-venus-api-version-check.md) records the observed response shapes.

The result appears directly below the amounts. The sell path starts with **Estimate pending**; the borrow path is a hypothetical market illustration. The sale card links to a separate **Sale check**: enter a public address there and select **Estimate partial sale**. The check sizes a candidate NVDAB sale against the same USDT cash target, using one probe quote and at most one candidate quote. It shows the candidate amount, an approximate output and whether the exact raw output reaches the target before costs. When both current results match, the main sell card shows the estimated output and candidate sale next to the borrow illustration. A fresh matching balance below the candidate suppresses the main-card amount; a missing or stale balance is marked unverified. The evidence and limits remain in the Sale check. Editing the target or units clears the estimate. The display expires at most 20 seconds after the local quote request began, including request time; a slower response is expired on arrival. An invalid target blocks the request. None of this establishes net proceeds or gives a sale instruction. The borrow card keeps the principal checks visible and puts exact values, oracle inputs and isolated risk illustrations under **Exact values, oracle inputs and borrow assumptions**. Balance and Venus Core reads are under **Optional balance and Venus Core reads**.

The Sale check doesn't build a transaction or read its minimum receive amount. On 2026-10-03, a [separate read-only technical build](docs/research/2026-10-03-target-minimum-check.md) estimated 100.000443760010104468 USDT for a 100 USDT target, while its minimum at 0.5% slippage was 99.500441541210053945 USDT. The app therefore warns that an estimate above the target can still leave the built minimum below it. This technical nonholder result doesn't establish an executable sale or final costs.

When the current typed NVDAB and USDT values match both fresh results, the page can show a compact combined line beside the quote summary: the target-sized candidate NVDAB amount and the Venus collateral-only minimum for the same cash target. The line requires Venus `retrieved_at` to be no more than five minutes old, a successful Binance candidate whose exact raw output is at or above the raw target, and an unexpired 20-second quote. It is a display comparison only. It says **before costs** and **no safety buffer**, does not prove wallet ownership, execution, net proceeds or personal borrowing safety, and disappears on input edit, failure, below-target output or expiry. See the [screen review](docs/product/2026-10-02-same-cash-screen-review.md).

When a fresh balance and target-sized quote refer to the same public address and inputs, the Sale check shows the NVDAB units that would remain if that candidate amount sold. It uses exact 18-decimal arithmetic, names the balance block and clears with the quote. If the observed balance is too small, the page says so. This is conditional arithmetic, not a settled balance or proof that the sale can execute. See the [slice rules](docs/product/remaining-units-slice.md) and [local QA log](docs/dx/field-log.md).

An optional public wallet address reads the NVDAB ERC-20 balance through the [official BNB Chain mainnet RPC](https://docs.bnbchain.org/bnb-smart-chain/developers/json_rpc/json-rpc-endpoint/). The server checks chain ID 56, reads contract code and `decimals()` metadata, then calls `balanceOf` at one recorded block. It reports that balance and whether it covers the entered sale units. RPC failure leaves the balance unknown. The address is sent in a POST body, not a URL. The public RPC receives the address in the balance request; this app does not write it to application logs or storage. A public address does not prove ownership or jurisdiction eligibility. This read does not inspect Venus positions.

The separate **Read Venus Core account state** action sends the same optional public wallet in a local JSON POST body to `POST /api/venus-account`. It verifies chain ID 56 and Core Unitroller code, then reads `getAssetsIn(address)`, the direct `userPoolId(address)` getter, `getBorrowingPower(address)` and `getAccountLiquidity(address)` at one recorded block through Core Unitroller `0xfD36E2c2a6789Db23113685031d7F16329158384`. The entered-market array is strictly bounded, the pool ID is validated as `uint96`, and both three-word risk results fail closed on ABI or contract errors. The display shows current net borrowing-power and liquidation-threshold states as **cushion**, **shortfall** or **zero**, plus Core market count, pool ID, block and timestamp. It does not return raw risk values or read gross supply/debt balances. These current net states are not a health factor, a USD amount, a post-deposit forecast or proof that a new borrow is available. A nonempty market list or nonzero pool ID flags existing Core configuration. An empty list and pool 0 do not establish no debt elsewhere or safe borrowing. RPC or ABI failures leave the account state unknown. The address is not returned, logged or stored. A [bounded public Core-account probe](docs/research/2026-10-03-venus-core-bounded-arithmetic-parity.md) matched both current risk tuples for one nonempty account with one active market. It did not involve a consenting NVDAB holder or validate risk after a new supply or borrow.

The optional **Estimate partial sale** action requires `BINANCE_WEB3_API_KEY` and `BINANCE_WEB3_SECRET_KEY` in the process environment or in the ignored repository-root `.env`. Each explicit click first makes one signed, read-only RWA search for `NVDA` on `bstock`. The server requires exactly one result with ticker NVDA, platform BStock, chain 56, the pinned NVDAB contract, symbol NVDAB and stock `assetType=1`; missing, ambiguous or malformed identity data blocks the quote call. Only after that check, it verifies NVDAB's decimals at a recorded BNB block and makes one signed `GET /api/v1/dex/aggregator/quote` for a probe of at most 1 NVDAB. It calculates a candidate sale in integer raw units, caps it at the typed holding and requests at most one more signed quote if the candidate differs. It doesn't keep increasing the amount until a target is reached. The wallet is sent to Binance in quote queries, but isn't put in this app's URL, response or logs. Missing credentials, identity failures, RPC errors, no route and documented API errors are shown as distinct states. A route observation isn't verified USDT proceeds: fee scope and execution remain unestablished. No quote is stored, and the app never requests approval, swap construction, order submission or transaction broadcast. Signing follows the [official authentication guide](https://web3.binance.com/en/dev-docs/authentication), [RWA search reference](https://web3.binance.com/en/dev-docs/llms-full.txt) and [Trading API guide](https://web3.binance.com/en/dev-docs/llms-full.txt). A [dated fractional technical read](docs/research/2026-10-02-fractional-target-quote.md) returned a 0.43 NVDAB SWAP quote near a 100 USDT target; it didn't use a holder or execute a sale.

The local server accepts at most six valid quote requests per rolling 60 seconds and processes one at a time. Further requests receive HTTP 429 before a signed Binance call. The limit applies across all clients of this server process and isn't a substitute for edge controls on a public deployment.

For a future HTTPS reverse proxy, the server also accepts `DYPLUX_PUBLIC_ORIGIN=https://demo.example.com` as a process environment setting. It must be one lower-case HTTPS domain origin without a path or query. Protected POST requests on that host require the exact matching `Origin` header; invalid settings reject those requests. The server still binds only to `127.0.0.1:8000`, and local browser access works as before. The origin check limits browser requests from other sites; it isn't authentication and doesn't make the server safe to publish. No public proxy or deployment is configured in this repository.

Run `python3 -m unittest discover -s tests -v` for local checks. The Binance quote-flow tests use synthetic responses and an in-memory RPC substitute. They exercise identity rejection, route amount matching, request limits and removal of quote IDs from the app response. The separate dated live request established authentication and one technical route, not holder execution or a safe cash decision.

The [Python tests workflow](.github/workflows/python.yml) runs the same 50-test suite on pushes to `main` and pull requests using Python 3.9. It has read-only repository permission and uses no Binance credentials or live API calls. Its [first run](https://github.com/dyplux/bnb-tokenized-stocks-2026/actions/runs/37101123092) passed on 2026-10-03.

For the separate read-only Venus arithmetic research check, run `python3 scripts/probe_venus_core_parity.py`. It samples a public governance account, pins one BNB block and compares both current-risk calculations against the deployed Core. It doesn't modify the app or prove a safe personal borrowing amount. The linked [report](docs/research/2026-10-03-venus-core-bounded-arithmetic-parity.md) records the sample's limitations.

The Venus panel remains a market-level illustration only, with no wallet debt or collateral, verified net sale proceeds, order, transaction, or execution. A fresh main-card sale amount is an estimate before costs, not a final received amount. The separate Sale check shows the route and source time; the estimate expires quickly. Borrow capacity, hypothetical health factor, liquidation-price stress, pool cash and flat-rate interest figures use isolated assumptions and do not establish personal safety or guarantee borrowing. The panel checks the typed NVDAB units against indexed Venus supply-cap headroom and separately reads the Core cap, vNVDAB supply and stored exchange rate at one recorded BNB Chain block. It verifies chain 56, deployed code and the vNVDAB underlying before displaying contract headroom. If any contract read fails, the contract check says **Unknown**; an indexed estimate never substitutes for a passing contract check. The panel also calculates the exact collateral-only minimum for the cash target from indexed oracle prices and the base collateral factor, rounded up to one NVDAB base unit, and compares it with the recorded cap. The minimum has no safety buffer, fees or account-wide risk check, and isn't a recommended deposit. Neither a passed cap check nor an indexed minimum establishes that a supply or borrow transaction can execute. [Venus says its indexed API can lag chain state](https://github.com/VenusProtocol/venus-protocol-documentation/blob/main/services/api.md); inspect both displayed source times.

On 2026-10-02, a [read-only technical quote](docs/research/2026-10-02-first-live-binance-quote.md) authenticated with Binance Web3 and returned one LiquidMesh `SWAP` route for 1 NVDAB to USDT. It used a temporary nonholder address and wasn't an executable user sale. The app marks this mode for review because the [endpoint reference](https://web3.binance.com/en/dev-docs/catalog/web3-wallet/api/rest-api/trading-api) says RWA routes always use `RFQ`; it still withholds net proceeds and any sell-versus-borrow recommendation.

A later [read-only `/swap` build](docs/research/2026-10-02-first-live-swap-build.md) returned an unsigned LiquidMesh transaction payload for a fresh technical quote. In that one response, quote `estimateGasFee=450000` matched `tx.gas=450000`, while `tx.gasPrice` was separate. The request did not sign, simulate or broadcast a trade, and the temporary address had no verified holdings or allowance. The app still treats the sale as an estimate with unverified proceeds.

## Prepare Binance Web3 credentials

On the SSD, store a full key pair only in the ignored repository file `/Volumes/SSD500/Dyplux/bnb-tokenized-stocks-2026/.env`, setting `BINANCE_WEB3_API_KEY` and `BINANCE_WEB3_SECRET_KEY`. An unquoted value is accepted by the local loader. Do not put either secret in chat, commits, logs or demos. Start the server from the repository root with `python3 app/server.py`, then open `http://127.0.0.1:8000`. The **Estimate partial sale** action performs one signed, read-only RWA identity search and, only when that identity is unambiguous, one or two signed quote requests for the entered cash goal and public wallet. It displays a vendor network-fee estimate in USD when supplied, separately from estimated USDT output; approval and final costs remain unknown. It doesn't submit, approve or broadcast a transaction. Keep the pair in `.env` only; use `.env.example` as the empty-field template.
